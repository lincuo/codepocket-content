# ADR-DAILY-002：嵌入式分层不是把 PC 后端照搬过来

## 核心误区：分层≠堆叠头文件

很多人做嵌入式，以为「分层」就是把代码切成驱动层、中间件层、应用层，然后一堆 `#include` 从上往下连。这是在用写 Web 工程的思路套 MCU——**Flash 和 RAM 不是按 GB 计的**。

## FreeRTOS 场景反模式

```c
/* ❌ 「标准三层」写法：应用直接调用驱动 */
void app_task(void *pv) {
    GPIO_WritePin(LED_PIN, HIGH);   // 应用层直连驱动细节
    vTaskDelay(500);                // 直接调用内核API
}
```

问题在哪？**应用层知道了 GPIO 是哪一个引脚，也知道了 delay 用的是系统 tick**。一旦硬件变更或调度策略调整，应用全得重改。这不是分层，这是**裸露的依赖**。

## 正确做法：抽象出领域语义

```c
/* ✅ 通过接口隐藏实现 */
void blink_led(void) {
    /* 应用只关心「灯亮」这个动作，不关心引脚号 */
    hardware_toggle(LED_HANDLE);  
    vTaskDelayFromISR(500);       // 延迟抽象为时间概念
}
```

## 实践建议：用「能力」而非「资源」定义接口

FreeRTOS 任务之间、任务与硬件之间的通信，应该围绕**业务能做什么**来设计，而不是基于「这个函数可以读寄存器」或「那个结构体包含多少字节」。每个模块向外暴露的应该是**领域语义 API**，内部用什么 ISR、DMA、寄存器位操作，全部藏起来。

**判断标准**：如果抽掉所有硬件相关的头文件，你的业务逻辑还能不能编译？如果不能，说明分层还不够。

---

> 《UNIX 编程艺术》：「程序应当建立在简单、清晰、易于理解的概念之上。」在嵌入式里，**简单意味着用最少的抽象换取最大的可维护性**，不是为了分层而分层。

**今日思考题**：把你的 FreeRTOS 任务列表打开，挑一个任务，把所有 `#include` 屏蔽掉，看它还能不能独立编译？缺了什么头文件，就是你的分层漏洞所在。
