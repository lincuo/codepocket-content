# 架构原则：嵌入式里的 DRY，代价是确定性

后端开发里，DRY（Don't Repeat Yourself）是一条铁律。两个模块有相似逻辑？抽成一个公共函数。三段代码长得像？上模板。

但在嵌入式系统里，DRY 的代价不是几行重复代码——是**调用链深度**和**分支预测失效**。

## 反模式：为复用而分层

在 STM32 + FreeRTOS 的项目中，常见一种"干净但致命"的设计：

```c
/* 传感器域 */
uint16_t adc_read_raw(uint8_t ch) { ... }

/* 抽象层 */
int32_t adc_convert(uint8_t ch, uint8_t ref) {
    uint16_t raw = adc_read_raw(ch);  // 第1层调用
    return scale_and_offset(raw, ref); // 第2层调用
}

/* 应用层 */
float get_temperature(uint8_t sensor_id) {
    int32_t val = adc_convert(sensor_id, REF_3V3); // 第3层
    return thermistor_curve(val);                   // 第4层
}
```

四个函数调用，四次栈帧分配，四次间接跳转。单次读取看起来无足轻重——但当这个读取跑在 1kHz 的控制环里时，你多出来的三帧调用吃掉了至少 15-20 个 CPU 周期，以及两次 L1 缓存未命中。

更危险的是：**当你需要在中断上下文中做快速采样时，这四层抽象全部作废。** 因为 ISR 不能调用可能阻塞、可能重入、可能分配栈空间的函数。于是你写了第二个"精简版"——DRY 的反面，变成了 DRIE（Do Repeat Yourself Intelligently Except）。

## 为什么后端分层和嵌入式分层目的不同

| 维度 | 后端分层 | 嵌入式分层 |
|------|----------|------------|
| 核心目标 | 可测试性、团队并行 | 确定性、资源隔离 |
| 每层代价 |  negligible（毫秒级） |  可测量的（微秒级） |
| 失败模式 | 响应慢 | 错过采样窗口、控制环路发散 |
| 抽象边界 | 按职责划分 | 按资源域划分 |

后端四层架构让不同开发者并行工作——Controller 的人不用等 Service 的人写完。嵌入式四层架构让调用链从 2 层膨胀到 5 层，栈深度翻倍，中断延迟不可预测。

**每一层增加的间接调用，都必须能用某种资源的隔离来偿还。** 如果只是为了"看起来整洁"而分层，那就是在偷时间——对于采样周期只有 1ms 的任务来说，多出来的三帧函数调用吃掉了几十微秒，这笔账迟早要还。

## 正确做法：按资源域而非抽象层级划分

```c
/* 传感器域 — 直接操作寄存器/外设，无间接跳转 */
static inline uint16_t adc_sample(uint8_t ch) {
    ADC->SQR1 = ch;
    ADC->CR2  = ADC_CR2_SWSTART;
    while(!(ADC->SR & ADC_SR_EOC));
    return ADC->DR;
}

/* 应用层直接调用，无中间抽象层 */
float temperature = thermistor_curve(adc_sample(SENSOR_TEMP));
```

这里没有"抽象层"、"HAL层"、"DAO层"。只有一个清晰的边界：**传感器域** 直接面对硬件，**应用域** 直接使用传感器域的输出。两者之间通过函数指针或宏定义解耦，但不通过额外的调用层级增加开销。

**一句话总结：嵌入式里的抽象，必须能用确定的资源预算来证明其合理性——否则它不是在组织代码，是在消耗时间。**

> 《UNIX编程艺术》："模块化是边界问题，不是职责划分。好的模块边界在需求变化时保持稳定。"

**今日思考题**：在你的项目中找一个正在被调用超过 100Hz 的函数链路，画出它的完整调用树——数一数从入口点到硬件操作有几层。如果超过 3 层且每一层都不能对应一个独立的资源域，考虑合并。
