### 核心摘录

> "The fundamental issue in software design is complexity. The main source of complexity is obscuration. Obscurations arise from depth."
>
> "A deep module is one that hides a lot of complex information behind a simple interface. A shallow module is one whose interface is not much simpler than its implementation. **Most modules should be deep.**"
>
> "When a module is too deep, it becomes difficult to understand. When a module is too shallow, there are too many of them, and the overall system becomes complex."
>
> — *Ousterhout, J. (2013). A Philosophy of Software Design. Addison-Wesley. pp. 4, 8, 15.*

### 解读：嵌入式固件中的"深度"权衡

Ousterhout 在这本书里提出了一个极其朴素却常被忽视的观点：**模块的"深度"（接口简洁度与信息隐藏量之比）是软件设计中最重要的单一度量。**

在嵌入式固件场景下，这个概念有非常具体的含义。

以你写过的一个 UART 驱动为例。一个"浅"模块长什么样？它暴露 `uart_init_baudrate()`, `uart_enable_tx()`, `uart_enable_rx()`, `uart_get_status_reg()`, `uart_clear_flag()`, `uart_set_dma_config()`——六个函数，每个都对应寄存器里的一个位域。调用者必须理解 UART 控制寄存器的每一位含义才能正确组合调用。这个模块的信息隐藏量几乎为零，但接口复杂度极高。

一个"深"模块呢？它只暴露三个函数：`uart_open(config)`, `uart_send(buf, len)`, `uart_close()`。`config` 是一个结构体，封装了波特率、数据位、停止位等参数。调用者不需要知道任何寄存器细节，甚至不需要知道这是一个 UART——他只知道自己在和"一个字节流通道"打交道。这个模块内部可能包含数百行寄存器操作代码，但这些复杂性被完美地封装在了接口背后。

问题在于：**深度不是免费的**。一个足够深的模块需要大量的设计思考——接口的抽象层次必须匹配使用者的认知模型，而不是硬件的手册目录。这就是 Ousterhout 说的"深度带来的复杂性"。如果 UART 驱动只封装了寄存器操作而没有提炼出有意义的抽象，那它就没有真正隐藏复杂性，只是把复杂性从寄存器搬到了配置结构体里。

嵌入式开发中常见的反模式是：**过度浅层化**。很多固件项目把每个外设寄存器映射成一个 C 结构体，每个位域对应一个宏，然后声称这是"面向对象的设计"。这实际上是 Ousterhout 批评的"伪深度"——接口看起来简单（访问结构体成员），但实现复杂度完全没有隐藏，调用者仍然需要了解每一层硬件细节。

另一个极端是**过度深层化**。一个"万能串口库"试图用一套 API 同时支持 UART、SPI 和 I2C，结果接口变得极其复杂，因为要覆盖所有边缘情况。这种模块的深度超过了它的抽象能力所能支撑的范围。

**好的嵌入式固件架构，本质上是在为每个硬件抽象找到正确的深度。** 这个深度由谁在使用它来决定——底层驱动面向 HAL 层，应该很深；HAL 层面向应用层，也应该深；但应用层面向业务逻辑，应该足够浅以至于开发者不需要思考硬件。

### 今日思考题

> 你的固件项目中，有没有哪个模块你觉得它"很深"——接口简洁、实现复杂？试着画出这个模块的调用者列表，问自己：**如果明天要替换掉这个模块背后的硬件（比如从 UART 换成 BLE 串口），调用者需要改几行代码？** 如果答案是"很多"，说明这个模块的深度不够——它隐藏的是硬件实现的细节，而不是真正的抽象。

带着这个问题入睡。晚安，科(D)。
